# Selective local memory

- Judge usefulness for the task. When no existing project knowledge or recovery is needed, ordinary Q&A, acknowledgements, casual chat and temporary tests need no RecallDock call or project binding; continue the ordinary work directly.
- Save Work only for actionable follow-up, unresolved operations, recovery evidence or a meaningful milestone. Propose long-term candidates only for stable preferences, durable constraints, reliable decisions and verified experience.
- Startup reports existing scope metadata, not knowledge. Read a bounded index only if the task actually needs prior verified knowledge; then fetch only specific necessary records.
- Never invent or select a host session ID. Only a real, trusted host lifecycle event can register its actual ID. If registration is absent, do not submit agent-attributed writes.
- For checked/tiered file evidence, copy the exact registered `ref` and matching `digest` from the trusted receipt. Do not derive a new URI from a path or cite an unregistered receipt file; a proposed topic key intentionally remains review-only.
- Propose durable, verified knowledge; keep progress, guesses, logs, transcripts and credentials out. Preconfigured manual/duplicates/checked/tiered policy admits eligible candidates automatically after local checks. Unverified evidence and topic conflicts stay in review; model approval fields never grant authority.
- `tools_find` searches tool/server names and descriptions, not stored memories. Use a short literal term. Backend hits are not added to the host tool list: use tools_describe(server=hit.server, tool=hit.name), then tools_call with the same server/tool, returned schema_hash, root and arguments. Query knowledge through that backend, not tools_find.
- Work tools are built into the gateway: call `work_find`, `work_read` and `work_checkpoint` directly, never through `tools_call`; only registered backends use `tools_call`.
- For useful task recovery, use gateway `work_find` (L0), selected `work_read` (L1, then L2 only as needed), and generation-checked `work_checkpoint` in independent `operations.db`. An empty find means no saved task, not blocked work. A meaningful new task can start at an authorized exact root/lane with expected=0; no existing Work record or knowledge project identity is required. Root identity, session scope and CAS checks still apply. Never load full transcripts.
- Gateway exposes only seven tools. `tools_find` reads visible summaries without starting backends; continue `after`, `tool_after`, and `builtin_after` independently while the corresponding `has_more` flag is true. `tools_describe server=recalldock_gateway` lists all seven short summaries; select `tool=NAME` for its exact schema. In strict mode, changed schemas require an explicit operator re-grant, including read-only tools; discovery never expands grants. Model confirmation fields never grant permission. Preserve original authentication and use native connectors for unsupported host authentication.
- Stateful calls return `_meta.recalldock_lease`; reuse only in the owning gateway session and release after use. Release closes the connection after active calls finish; it does not delete remote resources. A timeout or disconnection can have an unknown outcome: inspect external state before retry. Long-term memory is an on-demand backend and retains its stricter admission rules.
- `recalldock.db` is authoritative for long-term knowledge; `operations.db` is authoritative only for bounded task progress/catalog metadata. Old Markdown ledgers require explicit import; exports never overwrite manual edits.
- Hosts reuse verified bindings, including a linked worktree's bound main project. Unregistered conversations remain unbound; new persistent knowledge IDs require an explicitly authorized existing registration flow, not a name, cwd string or claimed session ID. Invalid/copied markers and conflicting scopes fail closed. Knowledge inheritance never merges exact Work root/lane. Historical activation stays read-only.
- The database is authoritative; Markdown is an export, not a second database. No automatic memory loading, conversation capture, or session-end summary.

## Recovery shortcuts

- When resuming a saved task, start with `work_find root=ABS_PATH limit=20`: recent checkpoint activity first, archived lanes hidden. `query=TEXT` searches current progress and event summaries/details; `status=archived|all` reveals archived lanes, `order=lane` selects alphabetical order. L0 remains <=2 KiB, so reuse returned `after` with the same order/filters while `has_more=true`; `total` counts all matches before pagination.
- Read `work_read root=ABS_PATH lane=EXACT_LANE`; request `mode=l2 generation=N` only for selected details. `view=history limit=20` returns an L0 timeline; reuse `before` while `has_more=true`. `view=event mode=l2 generation=N` reads that event's summary/details/kind and patch; it is not a transcript.
- Write with the observed `expected` generation. CAS errors include expected/current; reread before retry. An exact event+patch retry with the same operation ID and fingerprint returns `replayed=true` without advancing generation; a changed fingerprint is rejected.
- `writer.gateway_session_id` identifies the server-owned gateway instance, not the host's chat session. Missing `host_session_id` means unknown; only the operator can bind a real registered lifecycle session at gateway startup. Historical missing writers stay unknown; an unfinished registration is not proof someone is writing now.
- CLI fallback: `recalldock work find --root ABS_PATH --limit 20`, `recalldock work status --root ABS_PATH --lane EXACT_LANE`, `recalldock work history --root ABS_PATH --lane EXACT_LANE --limit 20`, and `recalldock work read --root ABS_PATH --lane EXACT_LANE --mode l2 --generation N --event`.
